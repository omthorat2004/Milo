# Next.js product app in Milo

`packages/frontend`, Next 16 App Router, React 19, Tailwind v4, port **3001**. The landing site is a
separate package on 3000, do not put product code there.

**Next 16 is not the Next.js in your training data.** `packages/frontend/AGENTS.md` says so and it is
right: read the relevant guide under `node_modules/next/dist/docs/` before writing routing, caching or
config code. Resolve it from the package directory, npm workspaces may hoist `next` out of view from
the repo root. That AGENTS.md block is regenerated by `next dev`, so deleting it from a diff just
recreates the change, commit it with your work.

## Route groups

```
src/app/
├── layout.tsx              html/body, fonts, metadata template, viewport
├── (marketing)/            public pages, own header/footer
├── (auth)/                 login + register, split-screen shell
└── (app)/                  product, sidebar offset via lg:pl-60
    ├── (all)/              account-wide views  -> /dashboard, /links, /logs
    └── [id]/               one resume's views  -> /:id/dashboard, ...
```

`(all)` and `[id]` render the same three pages against different scopes and share `AppNav`, which
builds hrefs through `hrefFor(segment, resourceId)`. **Adding a nav item means adding a page in both
groups**, or the sidebar links to a 404 in one scope. Only `(app)/layout.tsx` owns the sidebar
offset, the two inner layouts own `<main>` padding, keep it that way.

`params` is a Promise in Next 16. Await it, as `(app)/[id]/layout.tsx` does:

```tsx
export default async function ResourceLayout({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
```

`searchParams` is a Promise too. So are `cookies()` and `headers()`.

## Server by default

`"use client"` only when the file genuinely needs interactivity. In `components/app/` that is exactly
two files, `auth-form.tsx` (`useState`, `useId`) and `app-nav.tsx` (`usePathname`). Everything else
there is a server component. The marketing components carry more, since they own the scene and the
mobile header.

Push the boundary down rather than up. A page that needs one interactive control stays a server
component and imports a small client child, never the reverse. Never make a `layout.tsx` a client
component, and never mark a file `"use client"` just to silence an error, find which hook or handler
wants it and extract that piece.

Every page exports `metadata` (`export const metadata: Metadata = { title: "Dashboard" }`). The root
template turns it into `"Dashboard, Milo"`. A dynamic page uses `generateMetadata`.

## Design tokens

Tokens live once, in `packages/styles/globals.css`, and every app imports them. Do not redefine a
colour locally and do not reach for a stock Tailwind palette, `text-gray-500` is a bug in this
codebase.

The app supports light/dark via `@milo/ui/theme` and `ThemeToggle`. **Default to the semantic
tokens** — `bg-background`, `bg-surface`, `text-foreground`, `text-foreground-muted`,
`border-surface-border` — for anything that's part of the page surface (backgrounds, body text,
dividers), since only these flip with the toggle. The raw palette (`ink-*`, `sand-*`, `clay-400`,
`signal-*`) is fixed regardless of theme; reach for it only when the design wants a colour that
genuinely shouldn't change (the `signal-*` accent, `clay-400`). See the `theming` skill before
styling or restyling any component — plenty of existing chrome still hardcodes the raw palette from
before the toggle existed and is mid-migration, don't copy those classes into new code.

**Green means a recorded signal.** `signal-*` is reserved for something Milo actually measured, an
open, a download, a tracked event, plus the primary button. Never as decoration.

`font-display` is Instrument Serif and belongs to headings and big numbers. Body copy is
`font-sans`. Cards use `rounded-card`. Both fonts are wired as CSS variables in `app/layout.tsx`, do
not add a second `next/font` call.

Tailwind v4 has no config file. Content detection resolves relative to the imported stylesheet, which
would point into `node_modules`, so `app/globals.css` lists `@source "../../src"` and
`@source "../../../ui/src"` explicitly. **If a class from a shared package silently does not apply,
that missing `@source` is why.**

## Shared packages

`@milo/ui` ships TypeScript source with no build step and is compiled by each app through
`transpilePackages` in `next.config.ts`. A new subpath needs an entry in the `exports` map of
`packages/ui/package.json`, deep imports will not resolve.

Promote a component to `@milo/ui` only when a second app actually needs it. `components/ui/button.tsx`
and `lib/utils.ts` are local on purpose. Merge classes with `cn()` so callers can override.

Layout: `components/app/` product chrome, `components/marketing/` public pages, `components/ui/`
primitives. Import through the `@/*` alias, not relative parent paths. Scene code lives in
`*-scene.tsx` files (`marketing/raw-story-scene.tsx` today) and has its own rules, see the
`three-js-scenes` skill. A second scene is the point at which to add a `components/three/` directory,
as the landing package has.

## Talking to the backend

FastAPI on `:8000`, app on `:3001`. Different origins, so **every** request that carries auth needs
`credentials: "include"`, and the backend must list the origin in `CORS_ORIGINS`. The API sets
httpOnly cookies, so tokens are never in `localStorage` and never in a JS-readable cookie.

Errors arrive as `{ code, msg }` with an optional `details` object. Render `msg`, branch on `code`,
never on the status text. Validate every response at the boundary with Zod before it reaches a
component, and put the base URL in an env var, never a hardcoded `localhost:8000`.

A server component fetching an authenticated endpoint must forward the cookie explicitly, it does not
travel on its own:

```tsx
const res = await fetch(`${env.API_URL}/...`, { headers: { cookie: (await cookies()).toString() } });
```

`no any`, anywhere. `strict` is on in `tsconfig.json`.

## Privacy in the UI

The dashboard answers "how is my resume performing?", never "who is looking at it?". No viewer
identity, no location or map, no company or LinkedIn resolution, no fingerprinting. Copy must never
imply Milo can identify a viewer. Aggregate labels only: views, unique viewers, downloads, download
rate, page dwell. The `(auth)` layout and the dashboard copy already state this, keep new surfaces
consistent with them.

`next.config.ts` sets `Permissions-Policy: camera=(), microphone=(), geolocation=(),
interest-cohort=()`. That header is product policy, not boilerplate. Do not relax it.

## Accessibility

`auth-form.tsx` is the reference: `useId` for label/input pairs, `autoComplete` on every field,
`role="status"` on async feedback, `aria-describedby` wiring, `aria-hidden` on decorative marks,
`aria-label` on icon-only links. Focus is `focus:border-signal-400/60`, never a bare
`focus:outline-none` with nothing to replace it. Text stays HTML, never 3D geometry.

## Current state

Dashboard, links, and logs pages still render hardcoded zeros through `EmptyState` — no data layer
beyond auth yet.

Auth is live end to end for login: `lib/auth.api.ts` + `lib/axios.config.ts` talk to the backend, a
Zustand store (`stores/auth-store.ts`) + TanStack Query hooks (`hooks/use-auth-session.ts`,
`hooks/use-auth-mutations.ts`) track session state and drive `register`/`login`, and
`PrivateProvider`/`GuestOnlyProvider` (`components/providers/private-provider.tsx`) guard `(app)`
and `(auth)` respectively — see `docs/frontend-architecture.md`'s "Auth state" section for the full
wiring. This guard is **client-side only**, there is still no `middleware.ts`, so a protected page's
server-rendered shell can still reach the browser before the guard redirects; don't assume
request-time protection exists until that's added. Register is fully live too — it lands on
`/verify?email=...` (`components/app/verify-status.tsx`), which resolves live against
`verification-email/status` so the OTP step's resend cooldown survives a refresh instead of resetting.
Login routes into the same `/verify` flow on `email_not_verified`.

## Before declaring work done

```bash
npm run lint --workspace @milo/frontend
npm run typecheck --workspace @milo/frontend
npm run build --workspace @milo/frontend
```

or `make lint`, `make typecheck`, `make build` for every workspace. `npm run format` is Prettier and
must never touch `packages/backend`. Run `make dev-frontend` for :3001, and note that `npm run dev`
at the root starts the **landing** site instead.
